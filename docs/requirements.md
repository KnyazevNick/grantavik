# Grantavik — требования

**Версия документа:** 0.1, рабочий черновик.

Документ фиксирует решения по проекту. Разделы «Предлагаемый состав MVP», «Предлагаемые проверки» и «Открытые вопросы» ещё требуют проработки. Описанная функциональность не означает, что она уже реализована.

## 1. Назначение и границы

Grantavik — внутренний сервис для управления заявками на доступ сотрудников к корпоративным ресурсам. Проект разрабатывается одним автором как учебный и портфолио-проект с основным акцентом на серверную часть.

Базовая архитектура: модульный монолит на Python, FastAPI и PostgreSQL. Для работы с данными планируются SQLAlchemy и Alembic, для тестирования — pytest, для окружения запуска — Docker. Интерфейс пользователя минимален; безопасность имеет высокий приоритет.

Исходный объём не включает микросервисы и дополнительные внешние интеграции. Фактическая автоматическая выдача прав в VPN, GitHub или других системах не считается частью подтверждённой функциональности.

## 2. Участники и полномочия

| Участник | Ответственность |
| --- | --- |
| Сотрудник | Получатель доступа; может выступать инициатором заявки |
| Manager — руководитель | Проверяет рабочую необходимость доступа в своей зоне ответственности |
| Resource Owner — владелец ресурса | Проверяет допустимость доступа к своему ресурсу |
| IT Admin — IT-администратор | Технически выдаёт доступ после обязательных согласований |
| Global Head — главный руководитель | Один руководитель с полными правами и возможностью принимать все бизнес-решения |

В обычном процессе участвуют три ключевые роли принятия решений: Manager, Resource Owner и IT Admin. Global Head — отдельно оговорённая роль с расширенными полномочиями.

## 3. Согласованные бизнес-правила

| ID | Правило |
| --- | --- |
| BR-01 | Руководитель решает, нужен ли сотруднику доступ для работы. |
| BR-02 | Владелец ресурса решает, допустимо ли дать сотруднику доступ именно к этому ресурсу. |
| BR-03 | IT-администратор выдаёт доступ после всех обязательных согласований. Он не заменяет собой руководителя или владельца при оценке рабочей необходимости доступа. |
| BR-04 | IT-администратор может отказать по технической причине или причине безопасности: например, нет необходимого аккаунта или обнаружен конфликт прав доступа. |
| BR-05 | Обычные согласующие рассматривают заявки в своей зоне ответственности. У Global Head отдельно предусмотрены полные права. |
| BR-06 | Срок временного доступа по умолчанию — 90 дней. |
| BR-07 | Если руководитель создаёт заявку для своего подчинённого, его согласование считается полученным; заявка переходит владельцу ресурса. |
| BR-08 | Владелец ресурса может создать заявку для другого сотрудника и сразу одобрить её как владелец. Техническое решение остаётся за IT. Нужно уточнить, требуется ли в этом случае отдельное согласование руководителя получателя. |
| BR-09 | Отозвать доступ может выдавший его сотрудник либо лицо выше него по иерархии. Точное значение иерархии пока не определено. |
| BR-10 | Главный руководитель может отзывать доступ без указания причины. |
| BR-11 | Первой рассматривается заявка на новый доступ. Другие категории заявок отдельно не определены. |

## 4. Обычный процесс

1. Инициатор создаёт заявку на доступ сотрудника к ресурсу.
2. Руководитель рассматривает рабочую необходимость доступа.
3. Владелец ресурса рассматривает допустимость доступа.
4. После обязательных согласований заявку обрабатывает IT-администратор.
5. Доступ считается выданным после технической выдачи, а не только после согласования.

Для заявки руководителя за подчинённого применяется BR-07. Для заявки владельца ресурса за другого сотрудника применяется BR-08 с указанным открытым вопросом. Обход этапов и действия Global Head необходимо описать явно до реализации.

Названия статусов, переходы при отказе, отмене и истечении срока пока не зафиксированы. Ожидание технической выдачи следует отличать от факта выданного доступа.

## 5. Предлагаемый состав MVP

Это рабочее предложение для выбора объёма первой версии, а не утверждённый список.

- Сотрудники, ресурсы и назначение ответственных лиц.
- Создание заявки на новый доступ с указанием получателя, ресурса, обоснования и срока.
- Последовательное рассмотрение заявки с проверкой роли и зоны ответственности.
- Фиксация решения IT о технической выдаче или отказе.
- Учёт выданного доступа, срока действия и отзыва.
- История действий: кто, когда и какое решение принял.
- Автоматические тесты ключевых бизнес-правил.

Конкретные поля, статусы и механизмы реализации определяются после уточнения вопросов ниже.

## 6. Открытые вопросы

| Вопрос | Что нужно определить |
| --- | --- |
| Заявка владельца ресурса за другого сотрудника | Нужен ли этап руководителя получателя и в какой момент он выполняется? |
| Совмещение ролей | Что происходит, если руководитель, владелец ресурса или получатель — один человек? |
| Иерархия отзыва | Кто считается «выше» выдавшего доступ: руководитель сотрудника, руководитель IT или отдельная роль? |
| Полномочия Global Head | Как в процессе отражается его решение и какие действия остаются за IT? |
| Временный доступ | От какого события отсчитываются 90 дней, кто меняет срок и что происходит после его окончания? |
| Учёт и фактические права | Как подтверждать ручную выдачу и отзыв во внешнем ресурсе, чтобы запись в Grantavik соответствовала действительности? |
| Отказы и отмена | Какие статусы нужны, обязательна ли причина отказа и можно ли изменить или повторно подать заявку? |
| Вход и видимость данных | Как пользователи входят в систему и какие заявки и данные доступны каждой роли? |

## 7. Предлагаемые проверки поведения

Эти сценарии помогут проверять реализацию; окончательные результаты зависят от уточнения открытых вопросов.

- В обычном процессе доступ нельзя отметить выданным до получения обязательных согласований.
- Руководитель и владелец ресурса не могут согласовать чужую заявку вне своей зоны ответственности.
- Заявка руководителя за подчинённого не требует повторного согласования тем же руководителем.
- Согласованная заявка до технической выдачи не отображается как уже выданный доступ.
- При использовании срока по умолчанию временный доступ получает срок 90 дней от согласованного начального события.
- Попытка отзыва без достаточных полномочий отклоняется.

## 8. Как обновлять документ
